# Phase 1 — the research wave

**Status: closed, 2026-08-23.** Seven decision records, all landed, all adversarially verified, all carrying open items.

Phase 1 exists to serve one standing rule of the AIOS v2 Rescue plan: **no module is built before its research track lands.** The v1 platform's founding defect was not bad code, it was confident numbers nobody had measured — a coverage claim of "3 form specs" that was really 50, a "10¢ per citation" commitment that is 53–65¢ loaded, a doctrine file that transfers authority to a directory which does not exist, a cost ledger whose column type rounds the platform's highest-volume spend to $0.00. Each track was therefore given one question that blocked a build, a mandate to settle it against primary sources or mark it `[UNVERIFIED]` with the exact test that would settle it, and an adversarial verifier briefed to refute rather than agree. All seven came back **CORRECTED**: the architectures survived, and between them the verifiers found a 100× unit error in a cost model, a fabricated statistical interval, a per-type check table that would have failed its own golden test on day one, a containment rule that would have published an invented authority score, a set of pacing defaults that were arithmetically unsatisfiable, and a version-gated Elementor behaviour attributed to the wrong version range. This directory is the evidence base every subsequent phase is built on. Nothing here is a plan; everything here is a decision with its sources attached.

## Cross-track conflicts

This is the section no single track could write. Each conflict names the two positions, says which the evidence favours, and says plainly where it needs an owner instead.

### C-1 · The platform has two content cost models that differ by ~40×, and the headline provider figure is built on the smaller one

**R5 §5.2** models content at **4 pages per client per month (400/month agency-wide)** at **$0.0795 per page**, giving **$31.80/month**, inside a headline of **$279.39/month total provider spend ($2.79 per client)**. **R3A §6** models the platform's own default pacing — **6 pages per client per week (2,600/month)** — at **$0.504 per page** (five sub-calls, 78k in / 18k out, plus amortised research), giving **$1,310/month**, and separately warns that image generation at `MAX_IMAGES = 5` is 13,000 images/month and *could exceed the entire LLM bill*.

Substituting R3A's content line into R5's table takes total provider spend from **$279/month to roughly $1,560/month ($15.58 per client)** before images, and R5's model does not carry R6's substrate prefix cost ($80.14/month, §6.4) at all.

**Which the evidence favours:** R3A on the per-page token model — it itemises the pipeline stage by stage and its verifier recomputed it to the cent; R5's per-page figure prices a single 8k-in/3.5k-out drafting call and does not model the brief, rewrite, metadata or QA-judge legs. The *volume* difference is not an error in either track — it is two different assumptions about what the product does, and **only the owner can pick one** (see O-12). Until then, **no total provider-spend figure may be quoted to the client**, because the two tracks' own numbers disagree by 5.6×.

### C-2 · R4 tells the audit engine to read competitor GBP fields from Places; R5 forbids exactly that

**R4-50** specifies what may be measured on a competitor and includes *"for local, their public GBP fields via Places"*, and R4's cost model prices Place Details Pro for three competitors per Deep audit. **R5 §3.3** rejects Places for any client-facing ranking surface on ToS grounds — Maps Platform ToS §3.2.3 prohibits copying and saving business names, addresses and user reviews, and prohibits displaying Places content on a non-Google map — and **R5 req 28** demands a repository guard test asserting that no table stores a business name, address, rating or review whose `source = 'places'`. A `client_competitors` row populated by R4-50 would trip R5's own guard test.

**Which the evidence favours: R5.** Its restriction is sourced (albeit with the clause letters downgraded to `[UNVERIFIED]` pending a browser read — see U-3) and it is the track that owns provider terms. **Action:** re-source R4-50's competitor GBP fields to DataForSEO `business_data/google/my_business_info`, which R5 §3.4 already puts on the read path, or drop the competitor-GBP cell from the comparison table. R4's Places cost line ($0.100/Deep audit, free-capped in practice) disappears either way.

### C-3 · Two near-duplicate gates, two threshold sets, one shingling primitive that exists three times

**R2-10** specifies Broder resemblance over **w = 5** word shingles with MOD_16 sampling, blocking at **r ≥ 0.25** body / **≥ 0.60** heading skeleton, evaluated across three scopes including cross-client and cross-house-account. **R3A-22/25** specifies word **k = 5** shingles, blocking at **masked ≥ 0.80 / raw ≥ 0.90**, holding 0.60–0.80, with a structural rule at 0.50 and a run-mean rule at 0.45, scoped within one client's corpus. R3A's own verifier raised this as a coordination item.

These are **not** contradictory — the scopes and base rates genuinely differ, and a cross-client gate must trip far earlier than a within-client one. What is a real defect is that both are unbuilt, both propose their own implementation, both have separate calibration exercises (R2 O-1: 60 pairs; R3A O-2: 200 pages), and the repo already contains **two** reusable primitives neither track's requirement list points at: `backend/app/services/content_qa.py:611-618` builds 5-word shingles today, and `backend/app/modules/competitor_intel/service.py:317` is a working Jaccard.

**Which the evidence favours:** one shared implementation, two calibrated threshold sets. Build a single `shingle_jaccard(text, w) -> set[int]` + `resemblance(a, b)` module, reuse the existing primitives rather than adding a third, and run **one** golden-set exercise producing both scope-specific threshold tables. Both tracks require shadow/warn-only mode until calibration; that must be one flag, not two. Also carry forward R2's correction: **w=5 / m=16 are ours, not Broder's** (the paper states w=10, m=25), so the sweep must cover w ∈ {4, 5, 7, 10}.

### C-4 · Four tables claim to be the client's location, and three tracks build on different ones

- `client_business_profiles` (`0051`, `unique (client_id)`) — one row per client.
- `business_profiles` (`0045:74-93`, `label` + `is_primary`, no per-client uniqueness) — the citation engine's per-branch NAP.
- `gbp_profiles` (`0039:55`) — carries `place_id`, `nap_name`, `nap_address`, `review_count`, `avg_rating`.
- A proposed `client_locations`, which **does not exist**.

**R3A-12** recommends reusing `business_profiles` as the branch record (option a) and explicitly warns against a third source of truth. **R5 req 26** corrects an earlier draft that named `client_locations` and points at `gbp_profiles` instead. **R6-26 Wave 4** says `locations[]` *"defers to R3A-12's `client_locations`"* — i.e. it assumes option (b), which R3A recommends against. **R1 R8** requires pricing per location because Data Axle bills per Add and Moz/Synup price per location.

**Which the evidence favours: R3A option (a)** — reuse `business_profiles`, add `lat`/`lng` and a GBP place-id reference, have `client_local_facts.location_id` and `gbp_profiles` point at it, and demote `client_business_profiles` to the primary-location projection. But this is **decision D-9 and it is formally open** (O-10). It must be settled before R3A-13, R5 req 26 and R6-26 Wave 4 are built, because retrofitting after 100 onboardings is far more expensive than deciding now.

### C-5 · The citation cost model appears twice, 17–27× apart, and one of them budgets a prohibited practice

**R5 §5.2** prices citations at **$0.0068 per unit marginal**, 1,200 units/month, **$8.16/month** — and composes that unit price from a 30% `captcha_assisted` slice that budgets **paid CapMonster solves** (`config.py:630-637`). **R1 §7** prices the same module at **$1,655–$2,655/year** ($138–$221/month) at **5,300 units/year**, loaded **53–65¢ per live citation**, and its verifier flagged the solver line as *a violation of the standing no-CAPTCHA-evasion constraint*, ruling that component to **$0** with the human clearing the CAPTCHA instead.

R5 says so itself: its A13 volume assumption is unsourced, its $0.0068 sits ~15× *below* D-2's own 10¢ marginal target, and `config.py:635-637` holds *"the reference plan's own directional numbers"*, not measured ones.

**Which the evidence favours: R1 on every axis** — volume (derived from route feasibility, not assumed), unit price, and the CAPTCHA ruling. **Action:** replace R5's A13 and its citation line with R1 §6's route table and R1 §7.3's figures; and note that if the owner rules "no paid solving" (O-5), R5's 30% CAPTCHA slice becomes operator minutes, which pushes R1's loaded figure *up*, not down.

### C-6 · R3A says "do not enable prompt caching"; R6 says caching saves $409–$511/month

**R3A §6** computes that caching a ~50,000-token per-page prefix written once and read four times inside one page's five sub-calls costs **$1.003 versus $0.840 uncached** and concludes *"Do not enable caching per page."* **R6 §3.7/§6.1** computes a **$409–$511/month** saving on the client-independent global+agency prefix and makes two `cache_control` breakpoints a hard requirement (R6-17), with a production alert on `cache_read_input_tokens = 0`.

**Both are correct and R6's verifier already resolved it** — different prefixes, different amortisation. It is recorded here because an implementer reading R3A alone would disable the mechanism R6-17 requires, and the failure would be silent. **The rule to carry forward:** never cache the per-page prefix; always cache the client-independent global+agency prefix; and **do not split the Anthropic API key across workspaces** — cache isolation is per *workspace*, not per organisation, and a split erases the whole saving with no error raised (O-21).

### C-7 · Two cost ledgers, and the audit engine's is invisible to the platform's daily stop

**R4-10/R4-11** puts a `SpendLedger` inside the audit engine, writing to the engine's own SQLite `api_calls` table and exiting **12** on a zero-spend violation. **R5 §5.8** specifies the platform contract `dial → cache → per-client cap → daily stop → call → log ACTUAL` against Postgres `cost_log`. R4 also records that the engine reads its own `.env` (`audit_engine/config.py:16-21`), so the platform vault is bypassed for every paid run, and R5 records that `CostGate.evaluate` never reads `daily_stop` at all.

**Which the evidence favours:** both, wired together. R4-57's `run.json` must carry `usage.billable_calls` / `usage.by_provider` / `usage.est_cost_usd`, and the platform must commit that as **actual** spend (R5 req 17) on job completion. Without the wiring, an audit's spend exists in one ledger and the daily stop reads the other. **This is a Phase 2 spine item, not an R4 or R5 item**, because neither track owns both sides of the seam.

### C-8 · The automation ceiling is one level in the plan and three different granularities in the tracks

All four write-side tracks respect L3, but they mean different things by it. **R2-17** requires the approval endpoint to accept **exactly one `web2_id` per call** and forbids a batch-approve endpoint from existing, because Tumblr's API License §(s) requires per-post explicit permission. **R1 §5** explicitly frames Route B's benefit as *"a human approves a batch rather than performing each action"*. **R3B-42** allows *"each page or each explicitly-scoped batch"*, plus a WordPress-draft second gate. **R3A** stage 11 additionally requires that **the approver may not be the drafter**.

**Which the evidence favours:** all of them, which means the spine's ceiling representation cannot be a single integer. **Action:** the ceiling table is keyed by task class and carries at least `max_level`, `batch_allowed`, and `approver_may_be_actor`. `web2_publish` gets `batch_allowed = false` on a sourced platform-terms basis; `citation_submit` and `content_publish` get `true`; `content_publish` gets `approver_may_be_actor = false`. No confidence score, QA score or "verified" state raises any of them.

### C-14 · The human queue is the platform's real constraint and no track owns its total

**R3A §6:** 2,600 pages/month at 8 minutes' review is **347 hours/month ≈ two FTE reviewers**, and R3A-29 makes a *global* daily review-capacity throttle a P0. **R1 §7.3:** the Route C citation queue is **250 hours/year** and is **90% of the loaded citation cost** excluding Data Axle. **R2 §6:** Web 2.0 is **~51 operator-hours/year**, dominated by 640 L3 approvals. **R5 §5.3** concludes plainly that *"provider cost is not the constraint on the business at 100 clients… operator minutes are."*

**Which the evidence favours:** the capacity budget must be **platform-wide**, not per-module — a shared daily budget that content slots, citation queue items and Web 2.0 approvals all draw from, with contention surfaced on each module's calendar. And the **8-minute review estimate is itself unverified** (U-14) while carrying the entire labour argument. Staffing is an owner decision (O-13).

### Job contract and terminal states

- **New held/blocked states the enum must carry.** `blocked_facts` on `content_status` plus `held_facts` on `page_plans` (R3A-18); `held_knowledge_conflict` (R6 §3.3); `blocked` on the content-job vocabulary with a **closed** `blocked_reason` enum — `no_transport`, `credential_invalid`, `insufficient_caps`, `builder_missing`, `builder_version_unpinned`, `seo_write_path_unavailable`, `no_snapshot`, `roundtrip_delta`, `editor_load_failed`, `human_edit_detected`, `staging_required`, `budget_blocked`, `plugin_outdated`, `unsupported_cms` (R3B-5, R3B-29, R3B-43). ### Persistent finding identity

- **The fingerprint (R4-24):** `sha1(canonical_json({v: FINGERPRINT_VERSION, check: check_id, scope: locus_kind, locus: locus_value, disc: discriminator}))[:16]`, with `locus_kind ∈ {site, template, url, entity}`. **No URL, no evidence value, no page id, no run id and no count ever enters the hash** — each of those breaks `last_seen_at` semantics outright.
- **`UNIQUE (scope_type, scope_id, check_id, fingerprint)`**, ingest as an upsert that updates `last_seen_at` and sets `regressed_at` when a `closed_verified` row reappears (R4-68).
- **Instances are stored, not collapsed.** `audit_finding_instances(finding_id, url, evidence, first_seen_at, last_seen_at, closed_at, UNIQUE(finding_id, url))`; `instance_count` is derived and never written by hand (R4-27). Root-cause clusters are a **view**, never an identity (R4-29).
- **`fingerprint_version` participates in identity and is stored on every row.** Bumping it is a migration that closes existing rows with `closure_reason='superseded'` and opens new ones — never a silent hash change (R4-30).
- **"Fixed" requires four conditions, all of them** (R4-44): the check executed on the same basis, the locus was re-observed, the check returned `pass`, and a verification evidence blob was stored. Anything that merely stopped appearing is `closed_unverified` and is reported separately. `verify_finding(fingerprint)` is a targeted micro-run (R4-45), and a `structural_change` guard suppresses every "fixed" claim when >40% of open findings would close in one run and the template-id set changed (R4-47).
- **Scores are not comparable across bases.** `aggregate()` renormalises the composite over whichever categories produced findings (`scorers/aggregator.py:56-63`), so a free score and a deep score have different denominators. Add `scores.basis = {tier, types, checks_run, checks_skipped, providers_degraded}` to `run.json`, render "62 / 100 across the 197 checks this tier runs", and permit a delta only within an equal basis (R4-43).
- **Do not create a second findings-like queue.** R6-20 writes into R3A-49's `maintenance_items` rather than building its own. Adopt that as the general rule and decide explicitly whether citation drift (R1), Web 2.0 link loss (R2-16) and content decay (R3A-50) are `audit_findings` rows or their own tables — but decide once.
