# R3B — WordPress engine — Elementor safety envelope, SEO-plugin adapters, design translation

> Research track R3B · Phase 1 (Research wave) · AIOS v2 Rescue & Re-engineering Plan
> Written 2026-08-23. Every external claim below carries a primary source and the accessed date.
> Gates: the WordPress publish subsystem (spec §15, requirement family WP-1…WP-35).

---

## 1. Decision

We will build **one write path to a live client site and only one**: a builder-agnostic `PageModel` rendered to a target format, delivered through a hardened **`aios-publisher` v2 companion plugin** that is the sole transport, chosen **explicitly by capability discovery before any write** — never by a four-transport cascade. Capability discovery becomes a first-class, cached, invalidatable record (`site_capabilities`); a capability we need and cannot prove is a **visible `BLOCKED` job state with a named reason**, never a silent degrade and never `status = "done"`. Writes to Elementor are confined to an eight-point safety envelope whose first three points are absolute: **leaf-text edits only on AIOS-authored pages, no snapshot → no write, and any unintended round-trip delta aborts and rolls back**. New pages are created whole and additive; existing human-built pages are never structurally rewritten. SEO metadata is written through **five explicit per-plugin adapters** (Yoast, Rank Math, SEOPress, AIOSEO, none), each capability-probed at write time and **verified by read-back**, because the mechanisms are genuinely incompatible — Yoast exposes exactly three post-meta keys and **only for the `post` post type**, Rank Math exposes no REST-writable meta at all and requires its own `rankmath/v1/updateMeta` route, SEOPress uses five free `PUT` routes under `seopress/v1`, and AIOSEO uses an `aioseo_meta_data` field grafted onto core routes. The design profile drives a **design-system match — palette, type scale, spacing, section order, component style — not a DOM clone**; cloning a client's Elementor DOM is rejected on the evidence below. Everything in this track is capped at **L3 (a human approves each page or batch)**, and the ceiling is not raised by any confidence signal. Non-WordPress CMSs are out of v1 scope.

---

## 2. Context — the question this track had to settle

This is the only track in the plan whose failure mode is **a blank page on a paying client's live website**. Three things blocked the build:

1. **Is `_elementor_data` safe to write, and under what envelope?** The requirement set today contains only a revert (`WP-34`, `docs/recovery/DANIEL_PROJECT_RECOVERY_SPECIFICATION.md:1090`) — version pinning is **not** a `WP-` requirement at all; it appears only as the §15.4 verdict line (`:1039`, *"must be version-pinned and regression-tested"*) and as `IMP-10` (`:1991`). The spec itself already records the risk — "`_elementor_data` is an undocumented internal JSON contract that Elementor may change" (`DANIEL_PROJECT_RECOVERY_SPECIFICATION.md:1038`). Nobody had verified this at Elementor's own documentation, and nobody had specified what a safe write actually looks like.
2. **How does the system write SEO metadata without silently doing nothing?** `WP-16` is flagged *"critical, since writing core fields on a Yoast site silently does nothing"* (`DANIEL_PROJECT_RECOVERY_SPECIFICATION.md:1065`) and the gap analysis records `WP-016` as **NOT MET** (`docs/audit/REQUIREMENT_GAP_ANALYSIS.md:98`). The plugin currently sprays Yoast **and** Rank Math meta keys at every post and hopes (`wordpress-plugin/aios-publisher/includes/auto-publisher.php:181-192`).
3. **What replaces the silent four-transport cascade?** `_publish_wordpress` (`backend/workers/tasks/content.py:2165-2216`) tries the per-client connection, then the plugin, then the vault REST app-password, then falls to an artifact-only publish — and `_publish_artifact` writes `{"status": "done", ...}` (`backend/workers/tasks/content.py:2276`) even in the degraded branch. `docs/implementation/KNOWN_LIMITATIONS.md:17` (P0-4) records this as *"Stop faking success"*, **Not started**. The error handling is **not uniform**, and the differences matter: the per-client branch swallows a bare `except Exception` at `warning` (`content.py:2197-2198`); the plugin fallback catches only `WordPressPluginError` (`content.py:2206-2207`), so a transport/HTTP failure there propagates; and the final `_publish_via_rest` call (`content.py:2216`) is not wrapped at all. A client whose site rejected the first transport gets a green job; a client whose site fails on the last one gets an exception out of the publish path.

Until these are settled, building the publish path means building a machine that can break client sites and report success.

## 3. Findings

### 3.1 `_elementor_data` is an internal, per-widget, versioned-but-unguaranteed format — CONFIRMED

**Conclusion: the starting fact is correct and is now sourced. The format is documented, but as "Elementor Internals", with no stability contract, and the settings vocabulary is defined per widget by that widget's own controls — so there is no schema to validate against generically.**

- Elementor's own developer docs state the page content is *"an `array` of objects which holds all the elements on the page"*, recursive, with element fields `id`, `elType`, `settings`, `elements`, `isInner`, and `widgetType` for widgets. [elementor-page-content]
- The root object carries `title`, `type`, `version`, `page_settings`, `content`, and *"The data structure version. The latest version is 0.4"*. [elementor-general-structure] This is corroborated in Elementor's own source: `const DB_VERSION = '0.4';` in `includes/db.php`. [elementor-db-php]
- Widget settings are **not a fixed schema**: *"Each widget has a set of custom controls… this information is saved in the `settings` object as key-value pairs. The control id is used as the key value and the data is the value."* [elementor-widget-element] There is therefore no cross-widget schema; a validator must be built per widget per version.
- The Data Structure section sits under **"Elementor Internals"** on the docs index, and **no page carries a stability or backward-compatibility guarantee**. [elementor-docs-index] Neither the Data Structure index nor the page-content page states which post meta key holds it, nor warns against direct editing. [elementor-data-structure]
- The meta keys are named in source, not in the public docs: `ELEMENTOR_DATA_META_KEY = '_elementor_data'`, `BUILT_WITH_ELEMENTOR_META_KEY = '_elementor_edit_mode'`, `TYPE_META_KEY = '_elementor_template_type'`, `PAGE_META_KEY = '_elementor_page_settings'`, `CACHE_META_KEY = '_elementor_element_cache'` — `core/base/document.php:42-48`. [elementor-document-php]
- `_elementor_data` **must be `wp_slash()`-ed on write**: Elementor's own copy routine special-cases it — `if ( '_elementor_data' === $meta_key ) { $value = wp_slash( $value ); }` in `includes/db.php:374-375`. [elementor-db-php] The existing plugin already does this correctly (`wordpress-plugin/aios-publisher/includes/design-reconstruction.php:141`).

**What Elementor's docs are silent on and we must not invent:** whether a malformed tree renders a blank page or blocks the editor is **not stated anywhere in Elementor's documentation** `[UNVERIFIED]`. It is a widely reported behaviour but we found no vendor statement. *What would verify it:* write three deliberately malformed trees (truncated JSON, unknown `elType`, widget with a null `settings`) to a scratch page on a disposable Elementor install and record the front-end and editor behaviour. This is exactly the fixture-site regression suite required in §5.

### 3.2 Elementor now registers `_elementor_data` for the core REST API — from **3.27.3** — and this changes the plugin's justification

**Conclusion: since Elementor 3.27.3, `_elementor_data`, `_elementor_edit_mode`, `_elementor_template_type`, `_elementor_page_settings` (and, Pro-gated, `_elementor_conditions`) are `register_meta`'d with `show_in_rest`, so a sufficiently new site can be written through core `POST /wp/v2/pages/{id}` with a `meta` payload — no companion plugin required for that one write. This is new information that the recovery spec (`DANIEL_PROJECT_RECOVERY_SPECIFICATION.md:1023`, "cannot write Elementor's `_elementor_data` reliably… REST meta writes require the meta key to be registered — which usually needs a plugin anyway") predates. We record it as a correction, and it does not change the decision — see §4.**

Verified in Elementor's source at `modules/wp-rest/classes/elementor-post-meta.php`, **at `main` (the 4.2.3 line) unless a tag is named** [elementor-post-meta]:

- At `main`, `register_meta( 'post', '_elementor_data', [ … 'show_in_rest' => [ 'schema' => [ … 'type' => 'string', 'context' => [ 'edit' ] ] ], 'auth_callback' => [ $this, 'check_edit_permission' ], 'sanitize_callback' => [ $this, 'sanitize_elementor_data' ] ] )`. **Correction:** `object_subtype` is *not* set on this call — scoping is done by the `get_post_types_by_support( 'elementor' )` loop, not by an `object_subtype` argument.
- **Five keys are registered, not four:** `_elementor_edit_mode`, `_elementor_template_type`, `_elementor_data`, `_elementor_page_settings` and `_elementor_conditions` (the last is Pro-gated at `main`). Only `_elementor_data` (via `sanitize_elementor_data`) and `_elementor_page_settings` (via `sanitize_page_settings`) carry a `sanitize_callback`.
- Registration is **not experiment-gated**: `Module::__construct` hooks `rest_api_init` and calls `( new Elementor_Post_Meta() )->register();` unconditionally. [elementor-wp-rest-module]
- It applies only to post types returned by `get_post_types_by_support( 'elementor' )`.
- `check_edit_permission()` resolves the Elementor document and returns `$document && $document->is_editable_by_current_user()`; the docblock reads `@since 3.27.0`.
- **The version floor is 3.27.3, not 3.27.0** — and the history is messier than first recorded. At tag `3.27.0` the call is `register_meta( $post_type, '_elementor_data', … )` (object type = the post-type string — the bug). **Correction:** at tags `3.27.1` and `3.27.2` the file `modules/wp-rest/classes/elementor-post-meta.php` **does not exist at all** — the `modules/wp-rest/` tree at `3.27.2` holds only `elementor-settings.php`, `elementor-user-meta.php` and `module.php`, so there is *no* `_elementor_data` REST registration on those releases. From tag `3.27.3` onward the call is `register_meta( 'post', … )`. Verified by fetching the file (and the `3.27.2` git tree) at each tag. [elementor-post-meta-327x] The commit message *"Fix: REST API implementation prevents saving different post types via the Block Editor [ED-17886] (#30005)"* and its date **2025-01-23** are `[UNVERIFIED]` — we confirmed the code change across tags but did not open the PR/commit. *What would verify it:* fetch `https://github.com/elementor/elementor/pull/30005`.
- **Round-trip hazard — and it is version-gated, which changes how we must treat it.** At `main` / **4.2.3**, `sanitize_elementor_data()` returns the value unchanged `if ( current_user_can( 'unfiltered_html' ) )`; otherwise it JSON-decodes and runs `Utils::kses_post_deep()` over the tree before re-encoding, so a write by a non-`unfiltered_html` user **comes back different from what was sent**, legitimately. **Correction:** this function does **not** exist on the whole 3.27.3 → 4.2.0 range. Bisected by tag — `sanitize_elementor_data` occurs **0 times** at `3.27.3`, `3.28.0`, `3.30.0`, `4.0.0`, `4.1.0` and `4.2.0`, and **2 times** at `4.2.1`, `4.2.2` and `4.2.3`. It was introduced in **4.2.1**. [elementor-post-meta-sanitize-bisect] Consequence for the build: whether a core-REST write is `kses`-filtered is itself a **discovered capability** keyed to the site's Elementor version (`facts.elementor_rest_kses_applies`, true at ≥ 4.2.1), not a constant — and a naive byte-diff round-trip check produces false aborts on ≥ 4.2.1 and *no* protection benefit below it.

### 3.3 Writing `_elementor_data` does **not** invalidate Elementor's cached CSS or element cache

**Conclusion: a raw meta write leaves stale rendered CSS and stale cached element HTML in place. The write path must explicitly delete both, per post.**

- Post CSS is cached in post meta: `const META_KEY = '_elementor_css';` — `core/files/css/post.php:30`, with `load_meta()`/`update_meta()`/`delete_meta()` on that key. [elementor-post-css]
- Invalidation is **not** driven by the data changing: `CSS\Base::is_update_required()` `return false;` — `core/files/css/base.php:697-699`, and `Post_CSS` does not override it. [elementor-css-base]
- The only blunt tool is site-wide: `Files_Manager::clear_cache()` deletes **all** `_elementor_css`, **all** `_elementor_element_cache` and **all** asset meta across the site, then `delete_option( Frontend::META_KEY )` — `core/files/manager.php:107-131`. [elementor-files-manager] Running that on a client's live site to publish one page is unacceptable collateral.
- The supported operator-facing equivalents are Elementor → Tools → **Clear Files & Data** (formerly "Regenerate CSS & Data") [elementor-clear-files] and the WP-CLI command `wp elementor flush-css [--regenerate] [--network]`, documented as deleting cached CSS in `/wp-content/uploads/elementor/css/`. [elementor-flush-css] Both are site-wide.
- Therefore: **per-post `delete_post_meta( $post_id, '_elementor_css' )` and `delete_post_meta( $post_id, '_elementor_element_cache' )` is the correct, bounded action**, and it must run inside WordPress — i.e. in the companion plugin. The current plugin does neither: `aios_publisher_store_elementor_data()` writes `_elementor_edit_mode`, `_elementor_data`, `_elementor_version` and `_wp_page_template` and stops (`wordpress-plugin/aios-publisher/includes/design-reconstruction.php:121-147`).

**`[UNVERIFIED]`** — whether a write through the *core REST meta* route (§3.2) triggers any Elementor-side invalidation. Reading `core/base/document.php` and `core/files/css/base.php` says it does not, but we have no vendor statement. *What would verify it:* on the fixture site, write `_elementor_data` via `POST /wp/v2/pages/{id}` with a changed colour, then read `_elementor_css` meta and the rendered front-end CSS before and after.

### 3.4 Elementor V4 ("Atomic Editor") is the default for new sites since April 2026 — version pinning must record the editor generation, not just the version number

**Conclusion: there are now two live element vocabularies on the WordPress install base, and which one a site uses is a discovered capability, not an assumption.**

- Current released Elementor is **4.2.3**, last updated **2026-08-19 1:30pm GMT**, requiring WordPress **6.8+**, tested to **7.0.4** — the official WordPress.org plugin API, queried 2026-08-23. [wporg-api-elementor] The WordPress.org plugin page shows the same version and "10+ million" active installations. [wporg-elementor]
- Elementor Editor 4.0 shipped **19 March 2026**; *"new installations will automatically leverage Atomic Elements, Variables, Classes, and Components"* while existing sites *"introduce version 4 Atomic Elements alongside your existing v3 widgets on the same page."* [elementor-v4-devs]
- Elementor's V4 FAQ: *"Starting in April 2026, all new Elementor sites will run on version 4 by default"*; *"Nothing happens to existing sites"*; *"Both new and existing sites can combine legacy Widgets and Atomic Elements on the same page"*; atomic features are toggled at **WP Admin → Elementor → Editor → Settings → Atomic Editor**. [elementor-v4-faq]
- The v4 element slugs are visible in Elementor's own Playwright selectors: `e-div-block`, `e-flexbox`, `e-tabs`, `e-heading`, `e-paragraph`, `e-image`, `e-svg`, `e-button`, `e-divider`, `e-youtube`. [elementor-selectors] The v4 element classes live under `modules/atomic-widgets/elements/` (`atomic-heading`, `atomic-paragraph`, `atomic-button`, `atomic-image`, `div-block`, `flexbox`, `grid`, …). [elementor-atomic-elements]
- Elementor runs **automatic in-place BC migrations** of stored atomic prop data, keyed on `(post_id, data_identifier, manifest_hash)` where the fingerprint *"includes `ELEMENTOR_VERSION` and manifest MD5"*, triggered on `elementor/document/load/data`. [elementor-bc-migrations] Consequence: **the bytes we wrote are not necessarily the bytes we will read back later.** A drift check must tolerate an Elementor-authored migration and must be able to tell it apart from a human edit — see §5, requirement 24.

**`[UNVERIFIED]`** — whether a legacy `elType: "section"` / `"column"` tree still parses and renders on a site with the Atomic Editor enabled. The FAQ says legacy *widgets* coexist with atomic elements; it says nothing about the legacy *layout* elements. *What would verify it:* write a v3 section/column/widget tree to a page on a fixture site with Atomic Editor enabled and confirm both front-end render and editor load. This is a **blocking pre-build experiment**.

**`[UNVERIFIED]`** — the JSON shape of atomic elements. Elementor's public data-structure docs describe only the v3 vocabulary; the V4 developers update *"does not specify new elType/element naming conventions"*. [elementor-v4-devs] *What would verify it:* build one page by hand in the v4 editor on the fixture site and dump `_elementor_data`.

### 3.5 The legacy `accordion` widget is deprecated and hidden whenever containers are active — the allow-list must be capability-driven

**Conclusion: one of the seven widget types AIOS emits today is the wrong one on essentially every modern site.**

**Correction — the count is seven, not six.** `backend/app/services/elementor.py` emits `heading`, `text-editor`, `image`, `button`, `icon-box`, `accordion` (lines 278, 298, 318, 338, 573, 594, 613, 633) **and `icon-list`** — `_widget( "icon-list", { "icon_list": icon_items, … } )` at `elementor.py:824-829`, used to render the `process` (steps) section. Any allow-list, fixture set or golden-file suite that covers only the six will silently fail to cover a section kind the renderer already emits. The three `elType` values in use are `section`, `column` and `widget`; **`container` is not emitted today**.

- `includes/widgets/accordion.php` declares `public function show_in_panel(): bool { return ! Plugin::$instance->experiments->is_feature_active( 'container' ); }` (`@since 3.15.0`) and emits `add_deprecation_message( '3.15.0', 'You are currently editing an Accordion Widget in its old version…', 'nested-accordion' )` — the deprecation notice is itself conditional on `Plugin::$instance->widgets_manager->get_widget_types( 'nested-accordion' )` being registered. [elementor-accordion]
- The replacement `nested-accordion` is active only under the complementary condition: `Module::is_active() { return Plugin::$instance->experiments->is_feature_active( 'container' ); }`. [elementor-nested-accordion]
- Flexbox Containers became the default for new sites in Elementor **3.16**. [elementor-316]

So the correct widget for an FAQ block is `nested-accordion` on a container-enabled site and `accordion` otherwise, and the choice is a **probe result**, not a constant. The other six (`heading`, `text-editor`, `image`, `button`, `icon-box`, `icon-list`) are present as `heading.php`, `text-editor.php`, `image.php`, `button.php`, `icon-box.php`, `icon-list.php` and carry no deprecation marker in `includes/widgets/` at current `main`. [elementor-widgets-dir]

### 3.6 SEO-plugin write paths: four incompatible mechanisms and one dead end

**Conclusion: per-plugin adapters are unavoidable, and the naive "write every vendor's meta key and hope" approach in the current plugin is wrong in at least three distinct ways.**

WordPress core's behaviour is the common trap. `WP_REST_Meta_Fields::update_value()` iterates `$this->get_registered_fields()` and, for each *registered* field, `if ( ! array_key_exists( $name, $meta ) ) { continue; }` — **meta keys present in the request but not registered are silently skipped, with no error**. [wp-rest-meta-update] `register_meta`'s `show_in_rest` is defined as *"Whether data associated with this meta key can be considered public and should be accessible via the REST API."* [wp-register-meta] This is exactly the failure the existing seam documents at `backend/integrations/wordpress.py:26`.

| Plugin | Current version (wordpress.org, 2026-08-23) | Can AIOS write? | Mechanism | Breaks on update when |
|---|---|---|---|---|
| **Yoast SEO** | 28.3, updated 2026-08-18 [wporg-api] | **Partially** | Core `POST /wp/v2/posts/{id}` with `meta` — **only** `_yoast_wpseo_title`, `_yoast_wpseo_metadesc`, `_yoast_wpseo_focuskw`, and **only** `object_subtype => 'post'` | Yoast changes the `$meta_fields` `show_in_rest` flags, or the subtype scoping |
| **Rank Math** | 1.0.276, updated 2026-08-11 [wporg-api] | **Yes, own route only** | `POST /wp-json/rankmath/v1/updateMeta` with `objectID`, `objectType`, `meta{}` | Rank Math renames the route or tightens `Rest_Helper` |
| **SEOPress** | 10.1, updated 2026-07-29 [wporg-api] | **Yes** | `PUT /wp-json/seopress/v1/posts/{id}/title-description-metas` (+4 sibling routes) | SEOPress changes route shape (they already versioned to `#3`) |
| **AIOSEO** | 5.0.0.1, updated 2026-08-03 [wporg-api] | **Yes** | Core post routes with an `aioseo_meta_data` object in the body | AIOSEO changes the field name or the required capabilities |
| **none** | — | **N/A** | Write `<title>`/description into the page itself + JSON-LD; surface a `BLOCKED("no SEO plugin")` advisory | — |

**Yoast — the read-only claim is true of Yoast's *own* API, and there is a second, newer path the brief did not know about.**

- Yoast's developer portal states plainly: *"The Yoast REST API is currently read-only, and doesn't currently support `POST` or `PUT` calls to update the data."* It appends `yoast_head` and `yoast_head_json` to core responses and exposes `/wp-json/yoast/v1/get_head?url=`. [yoast-rest-api] The starting fact is **CONFIRMED**.
- **But** since **Yoast SEO 27.7** (released 2026-05-27) Yoast re-registers three of its own post meta keys for core REST: in `inc/class-wpseo-meta.php`, `$meta_fields['general']` marks `focuskw`, `title` and `metadesc` with `'show_in_rest' => true`, and the registration loop does `register_meta( 'post', self::$meta_prefix . $key, [ 'show_in_rest' => true, 'object_subtype' => 'post', 'sanitize_callback' => …, 'auth_callback' => fn => current_user_can( 'edit_post', $object_id ) ] )`. Verified in the 28.3 (current stable) tag at lines 296-299. [yoast-meta-283] Bisected by tag: `show_in_rest` occurs 0 times in `27.5` and `27.6`, 8 times in `27.7` and `27.8`. [yoast-tags]
- **`object_subtype => 'post'` is hard-coded.** Yoast meta written via core REST to a **page** is silently dropped. Generated local-SEO landing pages are `page` post type by default — this would have been an invisible, systematic failure across the whole product.
- Two further filters bite a verify step: `add_filter( 'update_post_metadata', [ self::class, 'remove_meta_if_default' ] )` and `add_filter( 'add_post_metadata', [ self::class, 'dont_save_meta_if_default' ] )` — **writing a value equal to Yoast's default is not persisted**, so a read-back of `""` may be correct behaviour rather than a dropped write. [yoast-meta-283]
- Reads are also gated: `add_filter( 'rest_prepare_post', [ self::class, 'hide_meta_from_unauthorized_rest_response' ] )`, because *"`register_meta`'s auth_callback only covers writes, so read access must be restricted separately"*. [yoast-meta-283]

**Rank Math — the brief's second starting fact is *half* right, and the half that is wrong is the important half.**

- The write route exists and is registered **unconditionally**: `includes/rest/class-shared.php` registers `'/updateMeta'` with `WP_REST_Server::CREATABLE`, callback `update_metadata`, `permission_callback => Rest_Helper::get_object_permissions_check`. The namespace constant is `const BASE = 'rankmath/v1';`. [rankmath-shared]
- `get_object_permissions_check()` dispatches on `objectType` ∈ {`post`,`term`,`user`} and, for posts, requires `current_user_can( $post_type->cap->edit_post, $post->ID )` **or** `edit_others_posts`, and that the post type be Rank Math-accessible. [rankmath-rest-helper]
- **The "Headless CMS Support" toggle gates the READ endpoint, not the write endpoint.** `includes/rest/class-headless.php` opens `register_routes()` with `if ( ! Helper::get_settings( 'general.headless_support' ) ) { return; }` and then registers only `'/getHead'` (`READABLE`, `permission_callback => '__return_true'`). [rankmath-headless]
- The toggle's default **is** `off`: `includes/settings/general/others.php` defines the field `[ 'id' => 'headless_support', 'type' => 'toggle', 'name' => 'Headless CMS Support', 'default' => 'off' ]`. [rankmath-others] Rank Math's KB places it at **Rank Math SEO → General Settings → Others** (advanced mode required) and describes it purely as *"a REST API endpoint that retrieves meta tags added by Rank Math for specific URLs"*; the same KB says *"Our REST API endpoint does not currently support the direct retrieval of specific meta tags."* [rankmath-kb-headless]
- **Correction of record:** the brief's premise — *"Rank Math has a write endpoint but requires a client-side 'Headless CMS Support' setting that is OFF by default"* — is **not supported by Rank Math's source**. The write endpoint requires no site-side toggle; only per-object edit capability. We must not build a "turn on Headless CMS Support" step into client onboarding for the *write* path. The `getHead` read path, if we ever want it, does require it.
- Rank Math's own meta keys are **not** REST-writable through core: a full grep of the plugin source (master, v1.0.276) finds **zero occurrences of `register_meta(`**, and every `show_in_rest` occurrence is in the bundled CMB2 vendor library or in unrelated modules (`includes/abilities/class-abilities.php`, `includes/modules/content-ai/class-content-ai-page.php`, and — one the first pass missed — `includes/helpers/class-wordpress.php:519`, which reads a *post-type object's* `show_in_rest` property, not a meta registration). [rankmath-source-grep] So `POST /wp/v2/posts/{id}` with `meta: { rank_math_title: … }` is silently dropped — exactly as `backend/integrations/wordpress.py:26` warns, and exactly what `wordpress-plugin/aios-publisher/includes/auto-publisher.php:183` does today when it fires `update_post_meta( $post_id, 'rank_math_title', … )` **from inside WordPress** (which does work, because it is not going through REST) — but the same key sent over REST would not.
- `update_metadata()` deliberately unhooks meta protection for its own keys — `remove_all_filters( 'is_protected_meta' ); add_filter( 'is_protected_meta', [ $this, 'only_this_plugin' ], 10, 2 );` — and **deletes** any key whose submitted value is empty (`if ( empty( $meta_value ) ) { delete_metadata( … ); continue; }`). Sending `""` to clear a field is a delete, not a blank. [rankmath-shared]
- Documentation status: Rank Math has **no public developer documentation page for `updateMeta`** that we could find. Rank Math staff name the route in their own support forum — *"The correct endpoint for updating meta fields is typically `/wp-json/rankmath/v1/updateMeta`"* [rankmath-support] — which is a vendor-hosted but non-authoritative source; the authoritative evidence above is the plugin's own GPL source.

**SEOPress — a clean, documented, free write API.** SEOPress's own guide lists, all **SEOPress 5.0+, free, requiring a user with `edit_post`**: `GET /wp-json/seopress/v1/posts/{postId}`, `GET …/posts/by-url?url=`, and the five `PUT` writers we need — `…/posts/{id}/title-description-metas`, `…/target-keywords`, `…/social-settings`, `…/meta-robot-settings`, `…/redirection-settings`. ### 3.7 Transport and authentication reality

**Conclusion: capability discovery must pick exactly one transport and record why, because each has a documented failure surface.**

- **Application Passwords**: *"As of 5.6, WordPress has shipped with Application Passwords"*, passed *"using Basic Auth / RFC 7617"* over `https://`. The official authentication page says **nothing** about hosts stripping the `Authorization` header — that is a real-world condition we must probe for, not a documented one. [wp-auth]
- **REST discovery** is well defined: a `Link: <http://example.com/wp-json/>; rel="https://api.w.org/"` header on front-end pages, an equivalent `<link>` in `<head>`, and an index at `GET /wp-json/` carrying `name`, `description`, a **`namespaces`** array (e.g. `["wp/v2","oembed/1.0/"]`), a `routes` object and an `authentication` map. [wp-discovery] **The documented index fields do not include a WordPress version number** — so WP version must come from another probe. (Stated precisely: this is what the discovery page documents, not a vendor statement that the version is absent.)
- **Revisions** exist as first-class REST resources: `GET /wp/v2/posts/<parent>/revisions`, `GET …/revisions/<id>`, `DELETE …/revisions/<id>`; autosaves have `POST /wp/v2/posts/<id>/autosaves`. **There is no REST restore endpoint.** [wp-revisions] Restoring therefore has to be a write of the old bytes, which is what our own snapshot store must do.
- Elementor's own revisions are ordinary WP revisions carrying `_elementor_data`: `RevisionsManager::get_revisions()` queries with `'meta_key' => '_elementor_data'`, caps display at `MAX_REVISIONS_TO_DISPLAY = 50`, forces `add_filter( 'wp_save_post_revision_check_for_changes', '__return_false' )`, and restores through `add_action( 'wp_restore_post_revision', … )`. [elementor-revisions] **WP revisions are a good second line of defence and a bad primary one** — they are capped, prunable by `WP_POST_REVISIONS`, and not under our control.
- Elementor exposes `elementor/v1/system-info` (`READABLE`, `permission_callback => current_user_can( 'manage_options' )`). [elementor-system-info] Useful, but it requires an **administrator** credential, which conflicts with least privilege (`WP-6`). We will not depend on it.

### 3.10 Staging detection

**Conclusion: one reliable in-WordPress primitive, plus host-specific heuristics that must be labelled as heuristics.**

### 5.2 The eight-point Elementor safety envelope

8. **(i) Leaf-text edits only, defined exactly.** A **leaf-text edit** is a write that changes the **string value of one allow-listed text control on one widget node**, where the node is identified by its stable `id`, the widget's `widgetType` is on the allow-list, and the control key is on the per-widget text-control allow-list: `heading.title`, `text-editor.editor`, `button.text`, `button.link.url`, `image.image.alt`, `image.image.title`, `icon-box.title_text`, `icon-box.description_text`, and the per-item `tab_title` / `tab_content` of the FAQ widget. **Not a leaf-text edit, and therefore forbidden in the edit path:** adding, removing, reordering or re-parenting any node; changing any `id`, `elType`, `widgetType` or `isInner`; changing any style/layout control (colour, spacing, typography, alignment, responsive variants); changing `image.image.url` or `image.image.id`; changing `page_settings`; touching a node whose `widgetType` is not on the allow-list; touching any node inside a Pro or third-party widget's subtree; and any edit to a page not carrying `_aios_managed`. Whole-page **creation** is a separate operation governed by the same allow-list but writing the complete tree in one shot to a **new** page.
9. **(ii) Snapshot-first — no snapshot, no write.** Before any write the plugin returns, and AIOS persists, a complete snapshot: `post_content`, `post_title`, `post_excerpt`, `post_name`, `post_status`, `_wp_page_template`, the full Elementor meta set (`_elementor_data`, `_elementor_edit_mode`, `_elementor_template_type`, `_elementor_page_settings`, `_elementor_version`), the active SEO plugin's meta for that post, and the AIOS meta set. Store as one gzipped JSON object in the existing artifact store under `wp-snapshots/{client_id}/{post_id}/{iso8601}-{sha256[:12]}.json.gz`, indexed by a new table **`wp_page_snapshots`** (`id`, `client_id`, `post_id`, `site_url`, `taken_at`, `artifact_key`, `content_sha256`, `elementor_sha256`, `reason text check (reason in ('pre_write','post_write','manual'))`, `expires_at`). **In the same operation** force a native WP revision so the site's own history also has it (Elementor forces `wp_save_post_revision_check_for_changes => false`, so a revision is always created — [elementor-revisions]). If either the snapshot or the revision fails, the job goes `BLOCKED("no_snapshot")` and **no write is attempted**. This is an unconditional gate, not a best-effort step.
10. **(iii) Round-trip validation with an explicit intended-delta set.** The write request carries an `intent` document: an ordered list of `{node_id, control_path, before_sha256, after_value}`. The plugin performs the write **and returns the post-sanitization tree it actually stored** (necessary because `sanitize_elementor_data` runs `kses_post_deep` for non-`unfiltered_html` users — §3.2). AIOS then diffs.

    **The diff algorithm.** (a) Canonicalise both trees: parse JSON; recursively sort object keys; drop keys whose value is `null` or `""` **only if absent in both**; normalise numeric strings; leave arrays in order (order is semantic in Elementor). (b) Flatten to a map `path -> value` where `path` is `/{index}/elements/{index}/settings/{key}[/{key}…]`, with each node additionally keyed by its `id` so a stable-id match survives an index shift. (c) Compute the symmetric difference. (d) **Intended** = exactly the `(node_id, control_path)` pairs in the `intent`, with `after_value` matching after HTML-normalisation (entity decode, whitespace collapse, attribute-order normalisation) — this is what absorbs `kses`. **Note the version gate (§3.2):** core-REST `kses` filtering via `sanitize_elementor_data` exists only on Elementor **≥ 4.2.1**. Below that version — and on the plugin transport, where the plugin controls the write — an unexplained HTML-normalisation difference is *not* attributable to Elementor's sanitizer and must not be waved through. Key the tolerance on `facts.elementor_rest_kses_applies`, never on a blanket assumption. (e) **Everything else is unintended**, including a node count change, an `id` change, an `elType` change, an appeared/disappeared key, and any change under `page_settings`. (f) Any unintended delta → **abort, restore from the §5.2-9 snapshot, mark `BLOCKED("roundtrip_delta")`, attach the diff to the job**. There is no "small delta" tolerance and no auto-retry.
11. **(iv) Widget allow-list — the initial list, and the rule for growing it.** Structural: `elType` ∈ {`section`, `column`, `container`} plus `widget`; nothing else. Widgets, v3 vocabulary: **`heading`, `text-editor`, `image`, `button`, `icon-box`, `icon-list`, and exactly one of `nested-accordion` (when `facts.elementor_container_experiment == true`) or `accordion` (otherwise)** — see §3.5. **`icon-list` is on the required list, not the optional one: the renderer already emits it today** (`elementor.py:824-829`, the `process`/steps section), so omitting it from the allow-list would break an existing section kind on day one. Genuinely optional additions permitted at build time: `divider`, `spacer`, `image-box` (all present in `includes/widgets/` at current `main` [elementor-widgets-dir]). **Explicitly excluded:** every Pro widget, every third-party widget, `html`, `shortcode`, `sidebar`, `wordpress`, `google-maps`, `video` and any form widget. **Rule for adding a widget:** it enters the allow-list only when all five hold — (1) the widget class file exists in Elementor **free** core at the pinned version; (2) `show_in_panel()` is not false and no `add_deprecation_message` is present at that version; (3) its full control-id set has been captured into a version-stamped fixture file at `backend/app/services/elementor_widgets/{elementor_version}/{widgetType}.json`; (4) a golden-file test writes a page containing it to the fixture site and the post-write verification of §5.2-13 passes; (5) a named human signs the addition off in `docs/recovery/DECISIONS_LOG.md`. A widget is removed from the allow-list the moment (2) stops holding at a newly pinned version.
12. **(v) Version pinning, with writes suspended on change.** `site_capabilities.facts` records `elementor_version`, `wp_version`, `theme` + theme version, `seo_plugin_version`, and `elementor_atomic_enabled`. AIOS maintains a **compatibility matrix** at `docs/wordpress/COMPATIBILITY_MATRIX.md`: one row per (Elementor minor, editor generation) with `verified_at`, the fixture-site run id, and the allow-list variant. On every plugin call the site returns a `facts_hash`; **a mismatch immediately marks the row `stale` and suspends writes for that client** with `BLOCKED("builder_version_unpinned")` until the new version either matches a verified matrix row or is verified on the fixture site. This satisfies and extends `IMP-10` (`DANIEL_PROJECT_RECOVERY_SPECIFICATION.md:1991`).
13. **(vi) Post-write verification, including "the editor still loads".** Three gates, all must pass:
    - **V1 — server-side parse (cheap, always).** Plugin endpoint `POST /aios/v1/verify` runs, inside WordPress: `$doc = Plugin::$instance->documents->get( $post_id ); $elements = $doc->get_elements_data();` and returns `{ok, node_count, widget_types[], exception}`. If Elementor's own parser refuses the tree, we know before spending a browser.
    - **V2 — front-end render.** `GET {permalink}` with a cache-busting query arg; assert HTTP 200, `Content-Length` above a floor, the page contains ≥1 `[data-element_type]`, contains the expected `<h1>` text, and contains **no** `elementor-alert` / empty-`<body>` signature. Capture a screenshot into the existing visual-QA path.
    - **V3 — the editor actually loads (headless).** Playwright, authenticated (a one-time editor-preflight nonce issued by the plugin to the connected user), navigates to `{site}/wp-admin/post.php?post={post_id}&action=elementor`. **Pass criteria, all required:** `#elementor-editor-wrapper` exists; `#elementor-loading` is removed or hidden; `#elementor-preview-iframe` exists and its document is reachable; the iframe body contains ≥1 `[data-element_type]`; `window.elementor` is defined and `window.elementor.documents.getCurrent()` returns a document whose id matches; **zero** uncaught page errors and zero `console.error` entries originating from `/wp-content/plugins/elementor/`; total time under a 45 s budget. These selectors are taken from Elementor's own editor template (`#elementor-loading`, `#elementor-editor-wrapper`, `#elementor-panel`, `#elementor-preview`, `#elementor-preview-responsive-wrapper` — [elementor-editor-body]) and its own Playwright selector file (`canvas: '#elementor-preview-iframe'`, `widget: '[data-element_type="widget"]'` — [elementor-selectors]). **V3 failure → automatic rollback (§5.2-14) and `BLOCKED("editor_load_failed")`.** V3 runs on every Elementor write in the first 90 days of operation; after that it may be sampled at 1-in-5 for repeat page types on a version already green in the matrix, but always runs on a first write to a client, a first write after a version change, and any write to a page with prior human edits.
14. **(vii) One-click rollback, surfaced for 7 days.** Storage as in §5.2-9. `wp_page_snapshots.expires_at = taken_at + 90 days` (retention), while the **UI surfaces the restore button for 7 days** from `taken_at` on the content job and on the client's page list. Restore path: `POST /aios/v1/restore` with `{post_id, snapshot_payload, snapshot_sha256}` → the plugin verifies the sha, writes back `post_content`/`post_title`/`post_excerpt`/`post_name`/`_wp_page_template` via `wp_update_post`, restores the full Elementor meta set with `wp_slash` on `_elementor_data`, restores the SEO meta through the same adapter that wrote it, then **deletes `_elementor_css` and `_elementor_element_cache` for that post** (§3.3) and fires the cache-purge hook. Restore is itself snapshotted (`reason='manual'`) before it runs, is idempotent, and is L3-gated like any other write. A native WP revision restore is offered as a **secondary** path only (`GET /wp/v2/posts/{parent}/revisions` — no REST restore endpoint exists, [wp-revisions]).
15. **(viii) Staging first where staging is detected.** Detection per §3.10/P10. If `facts.environment_type == 'staging'` for the connected site, writes proceed and are labelled staging. If a **separate** staging target is proposed for a production connection, add `wp_connections.staging_site_url text` + `staging_secret_sealed bytea` and require an operator to confirm the pairing **once**; thereafter every write for that client runs staging-first: write → V1+V2+V3 on staging → operator approves → the identical intent replays against production. A client with a confirmed staging pairing and an unreachable staging site is `BLOCKED("staging_required")`; heuristic-only detection with no confirmation never blocks, it only raises a one-time prompt.

Verify step must treat "value equals Yoast's default → not persisted" as **success**, not as a dropped write (`remove_meta_if_default` / `dont_save_meta_if_default`, §3.6).

19. **`SeoPressAdapter`.** Mechanism: `PUT {rest_root}/seopress/v1/posts/{id}/title-description-metas` for title+description; `PUT …/meta-robot-settings` for canonical, index/follow/archive/snippet/imageindex; `PUT …/social-settings` for OG; `PUT …/target-keywords` for the focus keyword. The plugin writes SEO meta **only** for the SEO plugin its own `/capabilities` probe reported active, and returns the post-write values so AIOS can verify.

### 5.4 Additive-only and human-edit protection

24. **Human-edit detection by hash.** On every AIOS write the plugin stores, alongside the content: `_aios_managed = 1`, `_aios_write_id` (the content-job id), `_aios_written_at`, `_aios_elementor_sha256` = sha256 of the **canonicalised** `_elementor_data` as stored after sanitization, `_aios_content_sha256` = sha256 of `post_content`, `_aios_seo_sha256` = sha256 of the SEO field set, and `_aios_elementor_version` = `ELEMENTOR_VERSION` at write time. **Before any subsequent write**, the plugin recomputes all three hashes from the live post and compares. Mismatch → the write is refused with `human_edit_detected` and the diff is returned for the operator. **The system never resolves a conflict by overwriting.** The operator's only two choices are *keep the human edit and cancel* or *snapshot-and-replace with explicit confirmation naming the page*. Because Elementor's BC migration engine can legitimately rewrite stored data on load (§3.4), a mismatch where `_aios_elementor_version` differs from the site's current `ELEMENTOR_VERSION` **and** the canonicalised trees differ only in atomic prop `$$type` keys is classified `builder_migration`, not `human_edit`, and re-baselines the hash after an operator acknowledges it once.
25. **Additive-only, enforced in the plugin, not in the caller.** The `aios/v1` controller must **refuse**, with a typed error: any write to a post lacking `_aios_managed` unless the request carries `create: true` and no `post_id`; any write to `wp_options` other than `aios_publisher_api_key` and `aios_publisher_options`; any touch of `elementor_active_kit` or any `elementor_*` global option; any filesystem write of any kind (the plugin has no filesystem write path and must not gain one); any taxonomy or menu mutation beyond attaching terms to its own posts; any user, role or capability mutation; and any write to `post_id = get_option('page_on_front')` or `page_for_posts`. There is **no** endpoint that edits an arbitrary post.
26. **Global styles are off-limits.** Nothing in AIOS may write the Elementor site kit, theme.json, the Customizer, theme files, or a global stylesheet. The current `_aios_design_css` mechanism stays **per-post** and must be re-implemented as an enqueued, versioned stylesheet file in the uploads directory rather than an inline `<style>` block (requirement 33).

There is no dynamic widget lookup and no pass-through of arbitrary `settings` keys — every emitted control key must appear in the version-stamped fixture file of requirement 11(3).

Only then does the write request leave the worker. **The honest statement of ambition:** this reproduces the client's **design system** — palette, type scale, spacing rhythm, button and card treatment, section order — on **our** section templates. It does not reproduce their DOM, their custom widgets, or their Pro layouts, and the UI must say so in those words on the preview screen.

## 6. Cost model at 100 clients

Volume assumption, stated so it can be challenged: **100 clients × 4 published pages/month = 400 page publishes/month ≈ 13/day**, plus one capability re-probe per client per week (**100/week ≈ 14/day**) and one design-profile extraction per client per quarter (**~33/month**).

| Line | Arithmetic | Monthly |
|---|---|---|
| Capability probes | 100 clients × 4.3 probes/month × ~10 HTTP calls = 4,300 calls | **$0** (client's own site) |
| Snapshots | 400 writes × ~200 KB gzipped × 3 months retention = 400 × 0.2 MB × 3 = **240 MB** resident. The 200 KB figure is an **engineering estimate, not a measurement** — no snapshot has been taken yet; re-derive it from the first 20 real snapshots | **≈$0** on existing object storage |
| Headless editor verification (V3) | 400 × 45 s worst case = 18,000 s = **5.0 CPU-hours/month** of one Chromium | absorbed by the existing VPS; ~0.7 % of a single core-month |
| Front-end render check (V2) | 400 × ~3 s = 20 min | negligible |
| PSI lab calls | 400 URLs × 1 strategy = **400 calls/month ≈ 13/day** | **$0** (free API; **quota `[UNVERIFIED]`** — see §3.9) |
| CrUX field checks | 400 URLs at day 28 = **400 calls/month**; at the documented 150 queries/min ceiling that is **under 3 minutes of budget** | **$0** [crux-api] |
| Screenshots for visual QA | 400 × 2 (intent + published) = 800 captures | absorbed by the existing Firecrawl/Playwright path |
| Design-profile extraction (Claude vision) | ~33 calls/month, one paid Claude call each, metered under the **existing `content` money-dial** with actual spend committed from `app/services/pricing.anthropic_cost` | model-price dependent — set by the model decision in another track, **not fabricated here** |
| Plugin distribution | 100 sites polling an AIOS-hosted manifest ~1×/day = 3,000 requests/month | negligible |

**Total incremental external spend attributable to R3B: approximately zero**, plus the design-extraction Claude tokens already metered under the content dial. The real cost of this track is **engineering time and VPS CPU**, not vendor fees. The one genuine unknown is the PSI quota; if it turns out to be low, the mitigation is to run Lighthouse locally on the VPS instead (5 CPU-hours/month more) rather than to buy anything.
